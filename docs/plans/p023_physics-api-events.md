# Physics API Events — Plan

Make collision events and contact-force events actually work for the new engine-agnostic Physics API (`PhysicsAPI.ts` / `PhysicsManager.ts` / `Physics/EngineRapier.ts` / `Physics/PhysicsAPITypes.ts` / `workers/physicsWorker.ts` / `workers/physics/physicsSwitch{World,Rigid,Coll}.ts`), then prove it end-to-end with an invisible sensor over the ground plane in the physics test scene that toasts the entering entity's name.

## Context

`ColliderParams` already exposes `isSensor`, `enableCollisionActiveEvents`/`enableContactForceActiveEvents`, and `collisionEventFn`/`contactForceEventFn` (`Physics/PhysicsAPITypes.ts:930-953`), and `EngineRapier.ts`'s `createCollider()` (lines 383-408) already sets up Rapier's `ActiveEvents` and lazily creates a module-level `Rapier.EventQueue`. **None of it works today** — this is dead scaffolding:

- `eventQueue` is created but **never drained**. `step()` (line 539) and `EngineWorldProxyAPI.step()` (line 590) both accept an `eventQueue` *parameter* and forward it straight to `physicsWorld.step(eventQueue, hooks)`, but nothing ever passes in the module's own `eventQueue` — the two are disconnected. No `drainCollisionEvents`/`drainContactForceEvents` call exists anywhere in the new API stack (confirmed via full-file review and repo-wide grep). `physicsWorker.ts`'s `STEP` handler (line 58-61) calls `engAPI.step()` with **no arguments at all**.
- In `WORKER_THREAD` mode (the project default, `src/CONFIG.ts:24`), passing a real `collisionEventFn`/`contactForceEventFn` in `ColliderParams` would currently **throw `DataCloneError`** the moment `PhysicsAPI.ts`'s `createCollider`/`createColliders` (lines 704-789) call `worker.postMessage({ ..., params })` — functions cannot cross that boundary. The `hasCollisionEventFn`/`hasContactForceEventFn` boolean flags already on the type (doc-commented "Do not set manually!") exist specifically to be the serializable stand-in for this, but nothing today computes them or strips the real functions before sending.
- The legacy `PhysicsRapier.ts` (lines 1634-1732, `deletePhysicsObject`/`setCurrentScenePhysicsObjects` cleanup) has a fully working reference implementation of this exact mechanism (event-queue creation, `drainCollisionEvents`/`drainContactForceEvents`, handle→object lookup, per-collider callback arrays, count-gated draining to skip cost when unused) — this plan ports that behavior onto the new API's id-based, thread-agnostic model, not onto the legacy file.

The goal is parity with the legacy system for these two event types specifically (not a general rewrite of `PhysicsRapier.ts`), working correctly in both `MAIN_THREAD` and `WORKER_THREAD` modes, verified with a real sensor + toast in `src/app/physicsTest.ts`.

## Design

**Serializable event records** (new, in `Physics/PhysicsAPITypes.ts`): `CollisionEventRecord = { collider1Id: number; collider2Id: number; started: boolean }` and `ContactForceEventRecord = { collider1Id: number; collider2Id: number; totalForce: PhysVector; totalForceMagnitude: number; maxForceDirection: PhysVector; maxForceMagnitude: number }` — plain data, safe to structured-clone. `TempContactForceEvent` (lines 638-667) is already method-shaped (`.collider1()`, `.totalForceMagnitude()`, etc.) to mirror Rapier's real API and its doc comment already warns its properties are only valid inside the drain closure; add a small `ContactForceEventSnapshot` class implementing `TempContactForceEvent` that wraps an eagerly-read `ContactForceEventRecord`, so `contactForceEventFn`'s signature stays identical on both threads — main-thread mode wraps the live Rapier event's values immediately (rather than passing the live object through), worker-thread mode reconstructs the same wrapper from the pushed record.

**New protocol type** (`PhysicsProtocolType.EVENTS_PUSH = 103`, in the existing ENGINE bucket right after `TRANSFORMS_PUSH = 102`): an unsolicited worker→main push, structurally identical in spirit to `TRANSFORMS_PUSH` (`PhysicsAPITypes.ts:2324`, handled in `PhysicsAPI.ts`'s `onWorkerMessage` at line 245) but **only sent when at least one event occurred that step** — unlike the transform buffer (continuously-valid, always pushed in `MESSAGE_BATCH` mode), collision/contact-force events are sparse and discrete, so there is no reason to pay a postMessage every frame when nothing collided. Payload: `{ type: EVENTS_PUSH; collisions: CollisionEventRecord[]; contactForces: ContactForceEventRecord[] }`. No `getSubType` change needed — 103 falls below the 200 `WORLD` range and is only ever a down-protocol (worker→main) message, never dispatched through the up-protocol switch.

**MAIN_THREAD mode** (`EngineRapier.ts`): real callback functions are available in-process (no serialization boundary), so keep them directly. In `createCollider()`, when `params.collisionEventFn`/`params.contactForceEventFn` is provided, store it in a new module-level `Map<number /* collider id */, Fn[]>` (arrays, to match the legacy file's multi-callback support for compound colliders) alongside the existing `collisionEventFnCount`/`contactForceEventFnCount` gate. Fix `step()`/`EngineWorldProxyAPI.step()` to always pass the module's own `eventQueue` into `physicsWorld.step(...)` (not the unused parameter), then — gated by the existing counters, exactly like the legacy pattern — call `eventQueue.drainCollisionEvents((h1, h2, started) => {...})` and `drainContactForceEvents((event) => {...})`, translating Rapier handles to `ColliderAPI`s via the existing `getColliderAPI()` (line 87), looking up both sides' registered callbacks by collider id, and invoking each side with the *other* collider as the second argument (mirrors `PhysicsRapier.ts:1634-1685` exactly). Wrap the live `TempContactForceEvent` in a `ContactForceEventSnapshot` before invoking `contactForceEventFn`, for signature parity with worker mode. Clean up registry entries in `deleteCollider()`/`deleteWorld()` alongside the existing counter resets (lines 503-522).

**WORKER_THREAD mode**: `PhysicsAPI.ts`'s `createCollider`/`createColliders` (lines 704-789) must strip `collisionEventFn`/`contactForceEventFn` out of the `params` object before `postMessage`, replacing them with `hasCollisionEventFn`/`hasContactForceEventFn` booleans (computed from `Boolean(params.collisionEventFn)` etc.) — this alone fixes the current `DataCloneError` risk. The real functions are kept in a new main-thread-only `Map<number /* collider id */, {...}>`, populated *after* the `CREATE_COLLIDER(S)` response resolves (the id is only known then), matching the same `res.id`/`collIds[i]` points where `ColliderProxyAPI` instances are already constructed (lines 722, 779). On the worker side, `EngineRapier.ts`'s drain logic runs the same as `MAIN_THREAD` except it has no callbacks to call — instead it collects `CollisionEventRecord[]`/`ContactForceEventRecord[]` into two arrays (translating handles to ids via the worker-local `colliders`/`colliderAPIs` maps, same as `getColliderAPI()` already does for other queries like `contactPairsWithSync`). `physicsWorker.ts`'s `STEP` case (line 58-61) calls this after `engAPI.step()` (alongside the existing `writeBackTransforms()`), and `sendMessageSimple({ type: EVENTS_PUSH, collisions, contactForces })` only when either array is non-empty. `PhysicsAPI.ts`'s `onWorkerMessage` (line 236) gets a new branch for `EVENTS_PUSH` that resolves both sides via the already-exported `getCollider(id)` (line 930) and invokes the registered callbacks, wrapping contact-force records in `ContactForceEventSnapshot`.

**Entity naming for the toast**: `ColliderParams.userData` is already cached synchronously on both `EngineColliderProxyAPI` (main thread) and `ColliderProxyAPI` (worker-mode proxy, `PhysicsAPI.ts:722/779` — set from `params.userData` at construction, no RPC needed for `getUserDataSync()`). The physics test scene will tag the ball/box colliders with `userData: { name: 'Ball' }` / `{ name: 'Box' }` so the sensor's `collisionEventFn` can read `otherCollider.getUserDataSync().name` directly, falling back to the collider id if absent.

## Phases

**Phase 1 — Types & protocol (additive, non-breaking).** `Physics/PhysicsAPITypes.ts`: add `CollisionEventRecord`/`ContactForceEventRecord` types, `ContactForceEventSnapshot` class, `PhysicsProtocolType.EVENTS_PUSH = 103`, the corresponding `PhysicsDownProtocol` union member, and an `EventsPushMessage` type alias (matching the `TransformsPushMessage` naming convention at line 2211). No behavior change yet.

**Phase 2 — MAIN_THREAD drain & dispatch.** `Physics/EngineRapier.ts`: fix `step()`/`EngineWorldProxyAPI.step()` to drive the module's real `eventQueue`; add the per-collider-id callback registries populated in `createCollider()`; implement the drain-and-dispatch closures described above; clean up on delete. Manually verify in the test scene under a temporary `workerTarget: 'MAIN_THREAD'` override.

**Phase 3 — WORKER_THREAD wiring.** `PhysicsAPI.ts`: strip real functions from `params` before `postMessage` in `createCollider`/`createColliders`, compute `hasCollisionEventFn`/`hasContactForceEventFn`, add the main-thread callback registry, add the `EVENTS_PUSH` branch in `onWorkerMessage`. `Physics/EngineRapier.ts`: export a drain function that returns the two plain record arrays instead of dispatching (used only from the worker). `workers/physicsWorker.ts`: call it after `engAPI.step()` in the `STEP` case and push `EVENTS_PUSH` when non-empty.

**Phase 4 — Physics test scene.** `src/app/physicsTest.ts`: tag the ball/box colliders with `userData: { name: 'Ball' | 'Box' }`; add a new headless (no mesh/`OBJECT3D`, no `target` passed) `createPhysicsEntity` call for a thin, invisible sensor `BOX` collider (`isSensor: true`) positioned just above the ground's top face (ground is `hy: 0.25` centered at origin, so e.g. `translation: { x: 0, y: 0.5, z: 0 }`, `hx: 5, hy: 0.25, hz: 5`, `rigidType: 'FIXED'`), with a `collisionEventFn` that, on `started === true`, calls `addToast` (`_engine/core/UI/Toaster.ts`) with the other collider's `userData.name` (fallback to its id).
