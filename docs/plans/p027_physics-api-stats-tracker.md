# Physics API Statistics Tracker — Plan

Measure the time the new engine-agnostic Physics API (`PhysicsAPI.ts` / `EngineRapier.ts` / `physicsWorker.ts`) spends stepping the world each frame, in both `MAIN_THREAD` and `WORKER_THREAD` `workerTarget` modes, and feed it into the existing `stats-gl` "PHY" panel — replacing the legacy `PhysicsRapier.ts` measurement that panel currently shows. Expose the raw measured value via a small accessor so a future, more accurate statistics window (mentioned by the user, not designed here) can reuse it without re-deriving the timing plumbing. Make the measurement itself opt-in (default off) so it carries zero cost unless explicitly enabled, addressing the risk that per-frame timing/messaging overhead could itself skew the numbers it's trying to report.

Additionally, in `WORKER_THREAD` mode, separately measure the main-thread↔worker messaging overhead around the `STEP` message (dispatch latency going down, write-back latency coming back up) as its own distinct metric — **kept separate from, never summed into, the pure step-calculation time**. Both the pure step duration and the messaging-latency figures must remain independently readable.

## Context (grounded in code)

- **The "PHY" panel already exists and is legacy-only.** `_dbg__Stats.ts:53` creates it via `stats.addPanel(new Stats.Panel('PHY', '#fff', '#212121'))`; `_updatePhysicsPanel(value: number)` (`_dbg__Stats.ts:82-104`) throttles `.update()`/`.updateGraph()` to `stats.logsPerSecond`/`graphsPerSecond` and is generic — it doesn't care what the value represents. The only caller today is `PhysicsRapier.ts:19,1798` (`updatePhysicsPanel(stopMeasuring - startMeasuring)`), via the always-bundled thin wrapper `debug/Stats.ts:54-56`.
- **The legacy measurement is contaminated and debug-only.** `PhysicsRapier.ts`'s `stepperFnDebug` (lines 1748-1799) wraps `performance.now()` around `baseStepper(loopState)` (the real `physicsWorld.step(eventQueue)` call, at line 1732) **and** the entire debug-wireframe-visualizer geometry rebuild (lines 1758-1792, only runs when `visualizerEnabled` is true) in one span. `stepperFnProduction` (line 1745) never measures at all. The panel today reflects only the legacy engine, contaminated by debug-draw cost whenever the wireframe visualizer is on — never the new Physics API.
- **The new API's one true `world.step()` call site** is `EngineRapier.ts:539-544` (`export const step = (...) => physicsWorld.step(...)`), reached two ways depending on `AppConfig.physics.workerTarget` (`Config.ts:29,79`, default `'WORKER_THREAD'`):
  - `MAIN_THREAD`: `PhysicsAPI.ts`'s `stepPhysics(loopState)` (lines 205-214) calls `engAPI?.step()` synchronously, in-thread, at line 208.
  - `WORKER_THREAD`: `stepPhysics()` instead fires a one-way `postMessage({ type: PhysicsProtocolType.STEP, isOneWay: true })` (line 212); `physicsWorker.ts`'s `STEP` case (lines 58-61) does `engAPI.step()` then `writeBackTransforms()` — no reply is awaited today. The `STEP` message payload carries nothing else today, so there's no timestamp on it to measure dispatch latency against.
- **`performance.now()` timestamps are comparable across a dedicated worker and its owning document.** Per the HTML spec, a dedicated worker shares its owning document's time origin, so `performance.now()` values recorded on the main thread and inside `physicsWorker.ts` can be subtracted directly to get a meaningful cross-thread interval — this is what makes measuring dispatch/write-back latency (not just intervals measured entirely within one thread) possible at all.
- **Two worker→main transports already exist, resolved once per world creation** (`physicsWorker.ts`'s `CREATE_WORLD` handler, lines 70-92, `resolvedUseSAB = Boolean(workerPhysicsState?.useSAB && typeof SharedArrayBuffer !== 'undefined' && self.crossOriginIsolated)`), gated by `AppConfig.physics.useSAB` (`Config.ts:42,84`, default `true`):
  - `SHARED_MEMORY`: the worker writes rigid-body transforms directly into a `SharedArrayBuffer`-backed `PhysicsTransformBuffer` (`PhysicsTransformBuffer.ts`) after every step; the main thread just reads it — **no per-step message exists in this mode**, by design (that's the whole point of the optimization).
  - `MESSAGE_BATCH` (fallback, no SAB): `writeBackTransforms()` (`physicsWorker.ts:165-178`) additionally does `sendMessageSimple({ type: PhysicsProtocolType.TRANSFORMS_PUSH, buffer: copy }, [copy])` — **an actual per-step postMessage already exists here**, consumed on the main thread by `onWorkerMessage`'s unsolicited-push branch (`PhysicsAPI.ts:238-249`, `type === PhysicsProtocolType.TRANSFORMS_PUSH`).
  - No Atomics are used anywhere in this hot path (confirmed: no `Atomics` references in `PhysicsTransformBuffer.ts`, `physicsWorker.ts`, or `PhysicsAPI.ts`) — reads/writes are plain, and the existing transform sync already accepts a one-frame-latency/no-tearing-guarantee tradeoff for a live debug-relevant value.
- **Boot-time config already has a reload-on-change LS override mechanism to extend.** `Config.ts:12-13` defines `DEBUG_PHYSICS_API_BOOT_LS_KEY = 'AEK_debugPhysicsApiBoot'`; `loadConfig()` (lines 167-180) reads it (gated by `isDebugEnvironment()`) and merges `workerTarget`/`useSAB`/`maxBodies` onto `config.physics`. `_dbg__PhysicsAPI.ts`'s `DebugPhysicsApiBoot` type (line 40) and `setBootOverride()` (lines 46-50, `lsSetItem` + `location.reload()`) back the matching Tweakpane bindings at lines 287-308 ("Boot-time settings (require a reload to take effect)"). This is the exact, already-built pattern to extend with a fourth field.
- **`initPhysics()` merges `AppConfig.physics` wholesale into `physicsState`, and that whole object is what's sent to the worker.** `PhysicsAPI.ts:167`: `physicsState = { ...physicsState, ...physicsConfig };`. For `WORKER_THREAD`, the full `physicsState` is sent once via `INIT_PHYSICS` (`PhysicsAPI.ts:188`, `messageWorkerAsync({ type: PhysicsProtocolType.INIT_PHYSICS, physicsState, ... })`) and stored as `workerPhysicsState` in the worker (`physicsWorker.ts:99`). **Any new boolean under `AppConfig.physics`/`PhysicsState` automatically reaches the worker with no new protocol message** — confirmed this is exactly how `useSAB`/`maxBodies` already reach `workerPhysicsState.useSAB`/`.maxBodies` for the `CREATE_WORLD` handler's `resolvedUseSAB`/buffer-sizing logic (`physicsWorker.ts:73-82`).
- **Boot-order rules out gating this on the Stats tab's config.** `InitApp.ts` calls `initNewPhysics(true)` / `createPhysicsWorld()` at lines 85-88 — well before `registerStatsModule()` (line 91) and long before `initStats()` actually runs (`MainLoop.ts:352`, inside `initMainLoop()`, called from `InitApp.ts:113`, itself after `appStartFn()`). A toggle read from `getStatsConfig()` at physics-init time would see stale/default data. Placing the new toggle under `AppConfig.physics` (read once by `loadConfig()`, which runs first in `InitEngine()`, `InitApp.ts:56`) avoids this ordering hazard entirely — this is also consistent with `workerTarget`/`useSAB`/`maxBodies` already living there rather than under Stats.
- **`stats-gl`'s `defaultStatsOptions` has a stale forward-reference** (`debug/Stats.ts:28`, `// @TODO: add trackPHY, trackTFPS, and FPS`) anticipating a Stats-tab-level flag. This plan does not implement that comment as written (see Context above for why — ordering), and leaves it in place for whatever future work (e.g. a Stats-tab-level show/hide, or TFPS/FPS tracking) still wants it; the enable/disable toggle this plan adds lives under the Physics API tab instead, next to `workerTarget`/`useSAB`/`maxBodies`.

## Design decisions

1. **New boot-time flag `stepStatsEnabled` under `AppConfig.physics`/`PhysicsState`, default `false`.** Follows the exact `workerTarget`/`useSAB`/`maxBodies` reload-on-change precedent (`Config.ts`'s `DEBUG_PHYSICS_API_BOOT_LS_KEY` merge + `_dbg__PhysicsAPI.ts`'s `setBootOverride()`), sidestepping the Stats-tab boot-order problem (see Context). Default `false` mirrors `trackGPU`/`trackCPT`/`trackHz` (`debug/Stats.ts:25-27`) all defaulting off — measuring is opt-in, not automatic, precisely because this task calls out the risk of the measurement itself having a perf cost.
2. **No new `PhysicsProtocolType` value.** Both transports already move data worker→main every step (`TRANSFORMS_PUSH` in `MESSAGE_BATCH` mode) or expose a shared-memory channel (`SHARED_MEMORY` mode) — the step duration piggybacks on both instead of inventing a fifth message type:
   - `MESSAGE_BATCH`: add an optional `stepDuration?: number` field to the existing `TRANSFORMS_PUSH` payload (`physicsWorker.ts`'s `writeBackTransforms()`), read in `PhysicsAPI.ts`'s existing `TRANSFORMS_PUSH` branch (line 247).
   - `SHARED_MEMORY`: allocate one extra tiny `SharedArrayBuffer`-backed `Float64Array(1)` ("physics step stats buffer"), created only when `resolvedUseSAB && workerPhysicsState?.stepStatsEnabled` is true at `CREATE_WORLD` time, returned alongside the existing transform `buffer` field on the `CREATE_WORLD` response. The worker writes the measured duration into it after every `engAPI.step()` in the `STEP` case; the main thread reads the latest value once per frame (same one-frame-latency/no-Atomics tradeoff the transform buffer itself already accepts).
   - `MAIN_THREAD`: trivial — wrap `engAPI?.step()` in `PhysicsAPI.ts:208` with `performance.now()`, same-thread, no messaging.
   - When `stepStatsEnabled` is `false` (default), none of the above runs: no extra `performance.now()` calls, no extra buffer allocation, no extra message field populated. This is the "togglable if there's a big perf hit" mechanism the task asked for, built as an always-available opt-in rather than something added reactively later.
3. **Expose a plain accessor, not just the panel side-effect.** Add `getLastPhysicsStepDuration(): number | undefined` to `PhysicsAPI.ts`, updated from all three code paths above, and holding **only** the time spent inside `engAPI.step()`/`physicsWorld.step()` — never inflated by messaging overhead. `updatePhysicsPanel()` (imported from `debug/Stats.ts`, mirroring the existing `PhysicsRapier.ts:19` precedent for importing the always-safe thin wrapper into core code) is just one consumer of this value, and the PHY panel continues to display this pure figure only — repeating the legacy panel's original intent without its contamination bug (see Context), not swapping one contamination for another.
4. **Messaging latency (`WORKER_THREAD` only) is measured as a separate, disjoint pair of intervals, never merged with step duration.** Two independent numbers, both gated by the same `stepStatsEnabled` flag:
   - **Dispatch latency (down, main → worker):** the main thread stamps `sentAt: performance.now()` onto the one-way `STEP` message right before `postMessage`. The worker's `STEP` case stamps its own `performance.now()` immediately on entry, *before* calling `engAPI.step()` — `dispatchMs = receivedAt - sentAt`. This interval and the step-duration interval (measured strictly around the `engAPI.step()` call itself) are adjacent, not overlapping, so there is nothing to subtract out or double-count.
   - **Write-back latency (up, worker → main):** the worker stamps `stepEndAt: performance.now()` right after `engAPI.step()` returns (this is the same instant `stepDuration`'s end-timestamp is taken). In `MESSAGE_BATCH` mode this rides as an extra field on the existing `TRANSFORMS_PUSH` message; the main thread stamps its own receipt time in the `onWorkerMessage` handler and computes `writeBackMs = receivedAt - stepEndAt`. In `SHARED_MEMORY` mode there is no return message, so this instead measures **read-cadence latency** (time between the worker finishing the step and the main thread next polling the shared stats buffer in `stepPhysics()`) rather than true postMessage transit cost — call this out explicitly wherever the value is surfaced, since the two transports don't measure quite the same thing (see Risks).
   - Exposed via a second, separate accessor `getLastPhysicsStepMessagingLatency(): { dispatchMs: number; writeBackMs: number } | undefined` (`undefined` in `MAIN_THREAD` mode, where no messaging occurs at all). `getLastPhysicsStepDuration()` is never modified to include these — a caller who wants "just the step calculation time" keeps calling the same accessor as before, unaffected by this addition.
5. **Replace, don't extend, the legacy measurement.** Remove the `performance.now()` pair and `updatePhysicsPanel()` call from `PhysicsRapier.ts`'s `stepperFnDebug` (lines 1748-1799) and the now-unused `updatePhysicsPanel` import (line 19). Leave the rest of `stepperFnDebug` (the debug-wireframe-visualizer rebuild) untouched — this plan is scoped to the measurement, not to `PhysicsRapier.ts`'s debug-draw behavior. The legacy stepper keeps running exactly as before, it simply stops writing to the PHY panel.
6. **No Stats-tab UI changes.** The PHY panel itself, its throttling (`_updatePhysicsPanel`), and its DOM/creation code are all reused as-is — only what feeds it changes. The enable toggle lives in the Physics API debug tab (`_dbg__PhysicsAPI.ts`), not the Stats tab, per Design Decision 1.

## Engine-side gaps to close first (Phase 1, additive/non-breaking)

- `Config.ts`: add `stepStatsEnabled?: boolean` to the `AppConfig.physics` type (near `useSAB`, line ~42) and default `false` (near line 84). Extend the `DEBUG_PHYSICS_API_BOOT_LS_KEY` override type/merge block (lines 167-180) with `stepStatsEnabled`.
- `PhysicsAPITypes.ts`: add `stepStatsEnabled: boolean` to `PhysicsState` (near `useSAB`/`maxBodies`, lines 47-97 area) so it flows through `physicsState = { ...physicsState, ...physicsConfig }` (`PhysicsAPI.ts:167`) and the existing `INIT_PHYSICS` payload with no new protocol message. Extend the `STEP` member of `PhysicsUpProtocol` with an optional `sentAt?: number`. Extend the `CREATE_WORLD` response member and the `TRANSFORMS_PUSH` member of the `PhysicsDownProtocol` discriminated union with the optional `statsBuffer?: SharedArrayBuffer` field and `stepDuration?: number` / `dispatchMs?: number` / `stepEndAt?: number` fields respectively (per Design Decisions 2 and 4).
- `PhysicsAPI.ts`: add module state `lastPhysicsStepDurationMs: number | undefined` + `getLastPhysicsStepDuration()` accessor (pure step time only, per Design Decision 3), and separately `lastPhysicsMessagingLatency: { dispatchMs: number; writeBackMs: number } | undefined` + `getLastPhysicsStepMessagingLatency()` accessor (per Design Decision 4). In `stepPhysics()` (lines 205-214): `MAIN_THREAD` branch wraps `engAPI?.step()` in `performance.now()` when `physicsState.stepStatsEnabled` and leaves the messaging accessor `undefined`; `WORKER_THREAD` branch stamps `sentAt` on the outgoing one-way `STEP` message when `stepStatsEnabled`, and — for `SHARED_MEMORY` transport with a stats buffer present — reads `stepMs`/`dispatchMs`/`stepEndAt` from it after firing the message and computes `writeBackMs = performance.now() - stepEndAt` itself. In `onWorkerMessage`'s `TRANSFORMS_PUSH` branch (line 247), read `data.stepDuration`/`data.dispatchMs` when present and compute `writeBackMs` from `data.stepEndAt` against the receipt-time `performance.now()`. All paths call `updatePhysicsPanel(stepDuration)` (never `stepDuration + dispatchMs`/`+ writeBackMs`) and update the two accessors' backing state independently.
- `physicsWorker.ts`: in the `STEP` case (lines 58-61), when `workerPhysicsState?.stepStatsEnabled`: stamp `receivedAt = performance.now()` on entry and compute `dispatchMs = receivedAt - data.sentAt`; wrap only the `engAPI.step()` call itself in a second `performance.now()` pair for `stepMs`, stamping `stepEndAt` right after. Pass `stepMs`/`dispatchMs`/`stepEndAt` into `writeBackTransforms()` so it can (a) write all three into the stats `SharedArrayBuffer` when one exists, or (b) include them as fields on the `TRANSFORMS_PUSH` message in the `MESSAGE_BATCH` branch (lines 165-178) — kept as separate fields throughout, never combined into one number. Extend the `CREATE_WORLD` handler (lines 70-92) to allocate a 3-slot (`Float64Array(3)`: `[stepMs, dispatchMs, stepEndAt]`) stats buffer and return it only when `resolvedUseSAB && workerPhysicsState?.stepStatsEnabled`.
- No behavior change for any existing consumer when `stepStatsEnabled` is left at its default `false` — purely additive.

Manual verification: with `?isDebug=true`, toggle the new boot flag on (see Phase 2) and confirm, from the console, that `getLastPhysicsStepDuration()` returns a plausible sub-millisecond-to-low-single-digit-millisecond number in all four combinations of `workerTarget` (`MAIN_THREAD`/`WORKER_THREAD`) × `useSAB` (`true`/`false`), and stays `undefined`/frozen when the flag is off; separately confirm `getLastPhysicsStepMessagingLatency()` returns `undefined` in `MAIN_THREAD` mode and a plausible `{ dispatchMs, writeBackMs }` pair in `WORKER_THREAD` mode (both `useSAB` settings), and that toggling `stepStatsEnabled` off/on doesn't change what `getLastPhysicsStepDuration()` reports for the same physics load — i.e. the two accessors are genuinely independent, not derived from a shared combined total.

## Non-goals

- **A dedicated, more accurate statistics window/UI.** Explicitly deferred by the user to a future plan; this plan's job is to make the raw per-step duration and messaging-latency figures available (`getLastPhysicsStepDuration()`, `getLastPhysicsStepMessagingLatency()`) and to feed the pure step duration to the existing PHY panel, not to design that future window.
- **Ever combining step duration and messaging latency into one displayed/returned number.** Explicitly requested by the user: the PHY panel and `getLastPhysicsStepDuration()` show/return only the `engAPI.step()` time; messaging latency is only ever available through the separate `getLastPhysicsStepMessagingLatency()` accessor.
- **A full worker→main round trip latency that includes main-thread consumption of the result**, beyond what `writeBackMs` already captures. `writeBackMs` stops at message-receipt (or, in `SHARED_MEMORY` mode, at the next poll) — it does not additionally measure how long `PhysicsManager.ts`'s `physicsToTransformSystem` or other consumers take to act on the data afterward.
- **Live (no-reload) toggling of `stepStatsEnabled`.** Mirrors the existing `workerTarget`/`useSAB`/`maxBodies` precedent (`_DONE_p022` Non-goals) — the stats `SharedArrayBuffer`, when used, is allocated once at `CREATE_WORLD` time, and there's no teardown/recreate machinery for the physics world/worker today.
- **Sub-step timing breakdown** (broad-phase / narrow-phase / solver / etc.). `world.step()` is one opaque call from the engine-agnostic API's perspective; only overall step duration is measured, matching what the legacy panel showed and what other future engine backends (per `Physics/ENGINES.ts`) could realistically report without engine-specific instrumentation.
- **Resolving the stale `trackPHY`/`trackTFPS`/`FPS` `@TODO`** at `debug/Stats.ts:28`. Left as-is for unrelated future work; this plan's enable toggle intentionally lives under the Physics API tab instead (see Context, "boot-order" bullet).
- **Touching `debugRender()`/visualizer wiring.** Out of scope, already tracked separately (`p025_debug-drawing-in-physics-api.md`).

## Risks / open questions

| Risk / question | Notes |
| --- | --- |
| One-frame latency reading the `SHARED_MEMORY` stats value, same as the transform buffer itself | Acceptable for a debug panel; identical tradeoff already accepted for live transform sync, no Atomics used there either. |
| No Atomics around the single shared `Float64`, so a torn read is theoretically possible | Display-only debug value; a rare stale/torn frame has no functional impact. Same precedent as the transform buffer. |
| Reload-required UX for `stepStatsEnabled` may surprise users expecting a live toggle | Same "Reload to apply" affordance already used for `workerTarget`/`useSAB`/`maxBodies`. |
| Even with `stepStatsEnabled` gating, does the `performance.now()` pair + occasional buffer/message write meaningfully perturb the number it's measuring? | Worth a quick sanity check in Phase 2's manual verification (toggle on/off, eyeball whether overall FPS via the TFPS panel visibly changes) — if it does, the buffer/message piggybacking (Design Decision 2) should already keep this cheap since no *new* per-frame message is added in `MESSAGE_BATCH` mode and none at all in `SHARED_MEMORY` mode. |
| `PhysicsResponse<T>` discriminated-union typing for the new optional `statsBuffer`/`stepDuration`/`dispatchMs`/`stepEndAt` fields | Should be additive/backward-compatible (all optional), but worth double-checking `tsc` is happy given how `PhysicsResponse<T>` is derived via `Extract<PhysicsDownProtocol, { type: T }>`. |
| `writeBackMs` means different things in the two transports — real postMessage transit time in `MESSAGE_BATCH`, but read-cadence/polling latency in `SHARED_MEMORY` (there's no return message to time) | Not a bug, but a real semantic gap between the two numbers; document this wherever `getLastPhysicsStepMessagingLatency()` is surfaced (including any future stats window) so the two transports' `writeBackMs` aren't compared as if they measured the same thing. |
| Cross-thread `performance.now()` subtraction assumes the worker's time origin matches the main document's | True for dedicated workers per spec, but worth a one-time sanity check (e.g. log both a `sentAt` and a same-tick main-thread `performance.now()` and diff against a known-zero baseline) during Phase 1's manual verification, since a wrong assumption here would silently produce nonsense `dispatchMs`/`writeBackMs` numbers rather than an error. |
| Measuring `dispatchMs`/`writeBackMs` adds a few extra `performance.now()` calls and payload fields per step beyond what pure step-duration tracking needed | Still fully gated behind `stepStatsEnabled` (default off) alongside the rest of this plan's measurement — no new always-on cost. |
