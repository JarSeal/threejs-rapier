# Large ECS Test World Scene

A new example scene under `src/app` purpose-built as a stress/soak test for large-world patterns: a big terrain, low-poly instanced foliage, a mix of static and dynamic physics objects, a shadow-casting directional "sun," one static and one dynamic camera, and the (already partially implemented) spatial index. Its job is to give the engine a real, reviewable data point on entity-count scaling, draw calls, shadow cost, and spatial-index rebuild cost — not to ship a new gameplay feature.

**Physics note:** `PhysicsRapier.ts` is expected to be replaced by a rewritten, engine-agnostic `PhysicsAPI.ts` soon (a separate upcoming plan, per CLAUDE.md's "Physics" section). Every toolkit helper this plan adds is deliberately physics-agnostic — no `PhysicsRapier.ts` import anywhere in `src/toolkit/geometry/` — so none of it needs rework when that rewrite lands; physics wiring (heightfield collider, per-object colliders) is left to whichever scene/phase code calls these helpers.

**Naming note:** the requested filename `p060-large-ecs-test-world-scene.md` collides with the existing `p060_debugger-undo-engine-core.md`. This plan is filed as `p090_large-ecs-test-world-scene.md` instead (next free slot after the culling/spatial family — `p050`/`p081`/`p080`, now all `_DONE_` — which this scene is designed to exercise). Flagging this rename per the request to notify before deviating from the given spec.

## 1. Why this is more than "add a scene" — scope decisions the request doesn't resolve

Six gaps exist between what was asked and what the engine currently supports. None of them block this plan, but each is a real design decision, not a mechanical detail, so they're called out before the phases rather than discovered mid-implementation.

1. **No instanced-mesh authoring in the JSON pipeline.** `src/_engine/schemas` / `MeshManager.ts` have no `instanceCount`/`instances` field — the scene/asset JSON → `generatedAppData` pipeline (CLAUDE.md's "Scene/asset data pipeline") has no concept of instancing today. The only precedent is `src/_engine/utils/ECSStressTest.ts`, a debug-only utility that hand-builds a raw `THREE.InstancedMesh` and drives per-instance transforms from ECS entities holding a slot index. **Decision:** the foliage/tree instancing in this plan follows that code pattern (a toolkit helper module + entities created imperatively from the scene's own `.ts` file), not JSON authoring. Extending the JSON schema to support instancing is out of scope — it's a separate, engine-level plan if it's wanted generally.
2. **No terrain/heightmap generator existed** — but a noise source didn't need to be added: `three` (already a dependency, `three/examples/jsm/math/SimplexNoise.js`) ships a `SimplexNoise` implementation, the same `three/examples/jsm/...` import style already used elsewhere in this repo (`mergeGeometries` from `BufferGeometryUtils.js` in `characterTestObjects.ts`). **Decision:** `generateTerrain` (§3 Phase 1, now built) uses that, seeded through a small local deterministic PRNG (`seededRandom.ts`, mulberry32 — `SimplexNoise`'s constructor accepts a custom `{ random(): number }`) so terrain is reproducible per seed. No new `package.json` dependency needed.
3. **Mesh JSON has no physics fields** (`meshSchema.ts` even has `// physicsParams: z.union([]),` explicitly commented out) — dynamic and static physics objects are always created imperatively via `PhysicsRapier.ts` (`createPhysicsObjectWithMesh`/`createPhysicsObjectWithoutMesh`), matching what `src/app/scene_thirdPersonGym.ts` already does. This plan follows that existing convention; it is not a gap this plan needs to close, and (per the physics note above) it's expected to be superseded by `PhysicsAPI.ts` regardless — actual collider wiring for this scene should wait for that plan.
4. **Directional-light shadows don't scale to an arbitrarily large terrain for free.** `lightSchema.ts`'s `shadowCameraFrustum` is a single fixed `[left, right, top, bottom]` box — there's no cascaded shadow map (CSM) in this engine. A shadow frustum sized to cover the whole terrain at once will produce blocky, low-resolution shadows; sizing it tightly gives good resolution but only near the origin/camera. **Decision:** scope the shadow frustum to a bounded "play area" around the scene origin (where the dynamic camera/objects actually are), explicitly *not* the entire terrain extent, and call this out in the scene as a known, intentional trade-off. CSM is out of scope (that's its own engine-level plan if the perf data from this scene motivates it).
5. **Update (now resolved): the spatial index has a real consumer, and full debug tooling.** `docs/plans/_DONE_p050_spatial-index.md` (Phases 1–3) and `docs/plans/_DONE_p081_light-object-culling.md` are both now `implemented` — every mesh and eligible light still auto-opts into `SPATIAL_INDEXED` (`MeshManager.ts`/`LightManager.ts`, opt-out via `CoreEntityOpts.spatialIndex`), the dynamic grid rebuilds every frame in `APP_POST_PHYSICS`, point/spot lights can opt into per-light contribution culling (`objectCullingEnabled` — JSON-authorable, `lightSchema.ts`), and `src/_engine/core/Debug/_dbg__SpatialGrid.ts` already ships an occupancy histogram, live cell-size tuning, a brute-force oracle (mismatch counter), and rebuild-time readout. **Decision, revised:** this plan no longer needs to build any ad-hoc validation code (the old §Phase 7 plan) — the existing "Spatial index" debug tab covers that directly. Instead, this scene gets real value by (a) being a genuine stress test of the now-implemented rebuild/membership cost at scale, measured via that debug tab, and (b) actually exercising `p081`'s contribution culling by including a handful of point lights with `objectCullingEnabled: true` (§2) rather than only the directional sun — something no existing example scene does yet. `p050`'s own Phase 4 (static/dynamic split, AABB-overlap insert, incremental updates, per-domain grids) was deliberately left unbuilt pending measured need; if this scene's occupancy histogram/rebuild-time numbers show it's warranted, that's the natural next plan to revisit, not something to pre-build here.
6. **"Scatter objects on the surface of another object" and "scatter across terrain" are the same primitive.** Both just mean "sample random points, weighted by area, across a `THREE.Mesh`'s surface" — three ships exactly this as `MeshSurfaceSampler` (`three/examples/jsm/math/MeshSurfaceSampler.js`), also zero new dependency. **Decision:** one generic `scatterOnSurface` helper (§3 Phase 2, now built) covers both cases the request named, rather than a terrain-specific scatterer plus a separate object-surface scatterer.
7. **New since the previous revision: `docs/plans/_DONE_p080_object3d-frustum-culling.md` is now implemented too** — meshes can opt into the ECS-queryable `TAG_FRUSTUM_CULLED` mechanism via `entityOpts.ecsFrustumCullingEnabled: true` (`CoreEntityOptsSchema`), independent of and distinct from native `MeshProps.frustumCullingEnabled` (Three's own render-time culling, unrelated). That plan shipped with **zero live usage anywhere in the engine** — no scene opts any mesh into it, and no gameplay system consumes the resulting `TAG_FRUSTUM_CULLED` state yet (`p080`'s own §5 risk table flags this as a live, unresolved risk, not a hypothetical one). **Decision:** this scene is the mechanism's first real exercise — see §2 and §3 Phase 5/7 — specifically to find out whether it behaves correctly and cheaply at the entity counts this scene is designed to reach, not to build a gameplay consumer for it (that stays out of scope, per §5).

## 2. Scene composition

- **Terrain**: one large, low-poly procedural ground mesh (`generateTerrain`, §3 Phase 1 — direct vertex-grid construction + `SimplexNoise` displacement, exposes a `getHeightAt(x, z)` sampler), with a matching heightfield-style collider to be wired up once `PhysicsAPI.ts` exists (§1.3) so dynamic objects rest on it correctly.
- **Foliage/trees**: 2–3 very-low-poly procedural geometries (a simple bush/shrub, a simple tree — merged cone/cylinder primitives à la `characterTestObjects.ts`'s `mergeGeometries` use), placed via `scatterOnSurface` (§3 Phase 2, generic surface scattering — also reusable for "on the surface of another object," e.g. debris scattered on a rock) and baked into `THREE.InstancedMesh`es in the thousands (`bakeScatterToInstancedMesh`), built as reusable toolkit modules.
- **Static elements**: a handful of fixed, non-dynamic props (rocks, platforms, walls) with static/fixed colliders, scattered around for visual reference points and to exercise the static side of world composition. A subset (placed far enough from the static overview camera to be reliably off-frustum from it) opt into `entityOpts.ecsFrustumCullingEnabled: true` (§1.7) — this scene's first exercise of `docs/plans/_DONE_p080_object3d-frustum-culling.md`'s ECS-queryable frustum-culling mechanism. Verify via the console entity inspector (`inspectEntity`, `src/_engine/utils/ECSHelpers.ts`) that `TAG_FRUSTUM_CULLED` toggles correctly as the static/dynamic camera pans, and that it costs nothing measurable in the `stats-gl` overlay at this scene's entity count — there's no dedicated debug checkbox for this yet (`p080` §2.5), so it's opted in from scene code/JSON, not toggled live.
- **Dynamic objects**: many simple dynamic rigid bodies (boxes, spheres) dropped/scattered onto the terrain, plus 2 more complex dynamic objects using compound/convex-hull colliders (following the merged-geometry precedent), to cover a body-shape variety beyond primitives.
- **Sun**: one `DIRECTIONAL` light, `castShadow: true`, tuned `shadowPreset`/`shadowMapSize`/`shadowCameraFrustum`/`shadowCameraNearFar` per §1.4's bounded-play-area trade-off.
- **Point lights (contribution-culling exercise)**: a handful of scattered `POINT` lights (e.g. lantern/firefly-style accents among the foliage, placed via the same `scatterOnSurface` used for foliage) with `objectCullingEnabled: true`, so the scene actually exercises `docs/plans/_DONE_p081_light-object-culling.md`'s now-implemented contribution culling (§1.5) instead of only the base spatial index. Toggleable per-light from the debug drawer's existing Light edit window checkbox, same as any other light in the engine.
- **Cameras**: one static camera (fixed `camProps.position`/`lookAtPoint`, a wide overview of the terrain) and one dynamic camera (follows a moving dynamic object using the existing `src/toolkit/ecs/effects/FollowTool.ts` follow behavior, which already does leader-relative lerped following and isn't light-specific despite living under "effects"). A key binding (via `src/_engine/core/InputControls.ts`, alongside the existing `debugKeys` pattern in `src/CONFIG.ts`) toggles `setActiveCamera` between the two for manual testing.

## 3. Phases

Non-breaking, individually reviewable. Phases 1–3 are pure toolkit additions (no engine or app changes); phases 4–7 build the scene incrementally.

**Phase 1 — Toolkit: procedural terrain generator. `[implemented]`**
`src/toolkit/geometry/generateTerrain.ts` (+ `seededRandom.ts`): builds a `BufferGeometry` directly from a vertex grid (not `PlaneGeometry` + rotation — see the module doc comment for why that would silently mirror sampled heights), displaced by `SimplexNoise`, and exposes `getHeightAt(x, z)` (bilinear-sampled) plus the raw `heights` grid for a future heightfield collider. No physics import — deliberately reusable once `PhysicsAPI.ts` exists (§1.3). Fully additive — nothing references it yet.

**Phase 2 — Toolkit: object/entity surface scatterer. `[implemented]`**
`src/toolkit/geometry/scatterOnSurface.ts`: `scatterOnSurface(opts)` samples `count` area-weighted random points across any `THREE.Mesh`'s surface (`MeshSurfaceSampler`, §1.6) — the terrain mesh or any other object — with optional minimum spacing (rejection-sampled, O(n²), fine at scene-build-time counts — see the module comment for the `SpatialGrid`-style bucketing follow-up if that ever matters), scale-range jitter, and either world-up or normal-aligned orientation. Two placement helpers consume its output: `bakeScatterToInstancedMesh` (bulk — writes instance matrices directly, sidestepping the fact that neither mesh JSON nor the ECS `Transform` helpers expose a per-entity scale today) and `spawnScatterAsMeshEntities` (individual ECS mesh entities, for small counts). Returns placement data only — no colliders, no ECS entities from `bakeScatterToInstancedMesh` — so it composes with whatever `PhysicsAPI.ts` ends up looking like without needing changes itself. Fully additive.

**Phase 3 — Toolkit: low-poly foliage/tree geometries + instanced-entity pool.**
New procedural geometries (bush, tree — merged primitives, no GLTF, following `characterTestObjects.ts`'s `mergeGeometries` use) plus a small instancing helper modeled on `ECSStressTest.ts`: given a geometry/material and the transforms `scatterOnSurface` produced, creates one `THREE.InstancedMesh` and one ECS entity per instance (holding its slot index), keeping per-instance matrices in sync if an entity's transform changes later. This is the piece that turns Phase 2's placement data into ECS-visible, per-instance-addressable foliage rather than just baked-once matrices. Fully additive.

**Phase 4 — Scene skeleton: terrain + static camera + sun, no dynamics yet.**
New `src/app/largeWorld.scene.json` + `largeWorld.ts`, following `testECS.scene.json`'s full-featured shape. Wires up: the Phase 1 terrain mesh, the directional sun with shadows (per §1.4), one static overview camera, and a skybox/ambient fill light for baseline lighting. Terrain physics (a real collider) is deferred to whichever scene-code convention exists once `PhysicsAPI.ts` lands (§1.3) — for this phase the terrain is render-only. Reviewable as "does the terrain render and shadow correctly" before anything else is added.

**Phase 5 — Foliage scatter + static props + point-light accents.**
Scatter Phase 3's instanced foliage/trees across the terrain using Phase 2's `scatterOnSurface` (surface = the terrain mesh, `getHeightAt` not even needed once scattering directly off the mesh surface) plus a handful of static props (rocks/platforms/walls) — physics-less for now, per §1.3. Also place the scattered point lights from §2, each with `objectCullingEnabled: true`. This is the phase that actually produces the "large" entity count and is where `SPATIAL_INDEXED` membership (auto opt-in), `p081`'s per-light contribution culling, and `p080`'s ECS frustum-culling opt-in on a subset of static props (§1.7, §2) all start being exercised at scale.

**Phase 6 — Dynamic objects + dynamic camera.**
Add the dynamic boxes/spheres and the 2 compound-shape objects, plus the dynamic camera via `FollowTool.ts` tracking one of them, and the camera-toggle key binding (§2). **Depends on the upcoming `PhysicsAPI.ts` plan** for actual rigid-body/collider creation (§1.3) — until that lands, this phase can proceed render-only (objects placed but not simulated) if it's reached first, and the physics wiring added once that API exists. This is the phase that, once physics lands, first exercises physics + spatial index together at volume (dynamic members rebuilding every frame, not just static ones).

**Phase 7 — Validation and perf pass. `[revised]`**
No new code needed for validation itself — `_dbg__SpatialGrid.ts`'s "Spatial index" debug tab (occupancy histogram, live cell-size tuning, brute-force oracle mismatch counter, rebuild-time readout) and the per-light "Object Culling" checkbox already ship (§1.5). This phase is just: run the scene with `?isDebug=true`, watch that tab plus the existing `stats-gl` overlay while flying the dynamic camera around, and tune entity counts / terrain size / cell size / shadow map size against the measured numbers (rebuild time, occupancy distribution, oracle mismatches, frame time, draw calls). Also specifically validate `p080`'s ECS frustum-culling opt-in from Phase 5 (§1.7): pan/fly both cameras so the opted-in static props go in and out of the **main** camera's frustum (not the debug fly-camera's — `p080`'s system deliberately tracks `getMainCamera()`, so this is the one behavior worth double-checking by eye, since a prop that's ECS-frustum-culled stays invisible even while the debug camera is pointed straight at it, per `p080` §0/§1's mesh-debug-visualization gap), confirm via `inspectEntity` that `TAG_FRUSTUM_CULLED` tracks the pan correctly with no stuck/incorrect state, and note whether it's measurably cheap at this scene's prop count (it should be — O(opted-in entities), not O(total meshes)). Record the resulting numbers as a short note at the bottom of this plan for future reference, and flag to `_DONE_p050_spatial-index.md`'s Phase 4 backlog (§1.5) if the data actually justifies one of those deferred optimizations.

## 5. Out of scope

- Extending the JSON asset schema to support instancing generally (engine-level change; this plan works around it in app/toolkit code instead).
- Cascaded shadow maps / any change to the shadow system itself — unrelated to `_DONE_p080_object3d-frustum-culling.md` (now implemented, §1.7), which is about ECS-queryable visibility state, not shadows.
- Building a gameplay consumer of `TAG_FRUSTUM_CULLED` (AI throttling, audio culling, LOD) — `p080`'s own risk table explicitly flags that no such consumer exists yet; this plan only exercises the mechanism's correctness/cost at scale (§1.7, Phase 5/7), it does not build a consumer for it.
- Building any new spatial-index consumer, debug tooling, or optimization work — `_DONE_p050_spatial-index.md`/`_DONE_p081_light-object-culling.md`/`_DONE_p080_object3d-frustum-culling.md` are all fully implemented (§1.5, §1.7); this plan only exercises and validates what already exists, including `p050`'s explicitly-deferred Phase 4 optimizations.
- Level streaming / chunked terrain / LOD — this is one large scene, not a streaming-world system.
- Any actual rigid-body/collider creation (terrain heightfield, dynamic boxes/spheres, compound shapes) — intentionally deferred to the forthcoming `PhysicsAPI.ts` plan (§1.3); Phases 1–2's helpers are built physics-agnostic specifically so that plan can consume them without rework.
