Notes for the Ækasha Hub's generator (`devTools/hub/`, `devTools/hubPlugin.ts`, `devTools/hubBuild.ts`, `devTools/hubPreview.ts`; authoring is in `hub/CLAUDE.md`); the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Ækasha Hub

- `yarn hub:build`: Any error (a dead `hub:` or `api:` link, an `.md` without a slot, …) is printed with its file and line, nothing is written, and it exits 1. It prints the API docs' stats and whether their model was reused. `--no-api` skips TypeDoc, for fast content work: the Documentation page says the API isn't built, and neither `api:` links nor `hub:` links to API pages are checked (one warning). `AEK_HUB=false` skips it (so `AEK_HUB=false yarn build` builds no Hub; `tsc -p hub` still runs) and turns off the dev server's `/hub/`. `AEK_HUB_IN_DIST=true yarn build` also copies it into `dist/hub/`, so the app's site serves it at `/hub/` (off by default: the Hub isn't in production unless asked for).
- Search (`search.ts`, `searchProtocol.ts`, the browser side `hub/_assets/ts/_search.ts`): minisearch, one document per heading with an id plus each page's own section (its title, `aek:tags`, `aek:description` and the text before its first heading), built from the rendered bodies (the homepage isn't indexed); code blocks give their identifiers only, and indexed words also get their camelCase parts. The serialized index is `_assets/hub-search.js`, whose URL is `hub-data.js`'s `searchIndex` (not in the pages, so a text edit only reloads its own page). The dialog is a chunk `hub.ts` imports on first use (⌘K / Ctrl+K, `/`, or the search button; its focus or hover preloads), so neither loads until someone searches. `hub:build` prints the index's size and warns over 1 MB. The Version page's changelog is out of it (`hubSearchSkip`): it was a large share.
- Output (`.cache/hub/dev/` in dev, `dist-hub/`): the pages, `404.html`, `_assets/hub.css`, `hub.js` (and its lazy `chunks/`), `hub-data.js` (`window.AEK_HUB`: versions, build, nav, every page with its headings, `latestChange`, `searchIndex`), `hub-search.js`, the static assets, and the favicons copied from `hub/_assets/favicons/` (the Hub's own: the app's Æ in the Hub's accent, not `src/public/`'s). Every link is relative, so the site works at a domain root and under `/hub/`; the 404 page, served at any depth, resolves against `<base href>` (`rebaseNotFoundPage` moves it). Every `_assets/` reference carries `?v=<content hash>` and `_headers` caches `_assets/*` as immutable, so reference a static asset through `{{asset:…}}` (or `url(fonts/…)` in the SCSS, which gets its hash), never as a bare path.
- Modes: `public` (`yarn hub:build`: minified, no dev client; any error writes nothing) and `dev` (the plugin: unminified, the dev client; a page with an error is served as an error page listing it with its file and line, and errors outside every page, in the shell, SCSS or TS, go on every page and the 404 page; a failed SCSS or TS build keeps the last good assets).
- Dev plugin (`devTools/hubPlugin.ts`, `AEK_HUB=false` turns it off): lazy, the first `/hub` request empties `.cache/hub/dev/` and builds, then the watching starts. `hub/` is watched with `fs.watch`, not Vite's watcher (Vite logs a watched `.html` save as a "page reload", clearing the terminal, and sends a `full-reload`); the build's sources outside it (`package.json`, `CHANGELOG.md`, `docs/issues/`, the files pages include with `<<<`, `tsconfig.json`) go through Vite's watcher. Other app, toolkit and engine saves never rebuild it (an engine or toolkit save only marks the API docs stale, see Documentation). Every run builds the whole Hub (tens of ms) and `diffBuilds` compares it with the last run to send the custom HMR event `aek:hub` (`HubDevEvent`, `devTools/hub/devProtocol.ts`): `css` (the stylesheet is swapped, no reload), `pages` (only those tabs reload) or `all` (scripts or static assets). It never sends `full-reload`, so open app tabs aren't touched. The dev client (`hub/_assets/ts/_devClient.ts`, dev builds only) opens its own socket to Vite's HMR server instead of importing `/@vite/client`, which reloads on the gatherer's `full-reload`s and shows the app's error overlay. The socket's token is filled into each page when it's served (never on disk), and `/hub` routes run devFiles' `checkHostAndOrigin`. `hub/hub.config.ts` and `devTools/hub/*` are Vite config dependencies: a change restarts the server, and open Hub tabs reload when it's back.
- Generated sections (`devTools/hub/generated/`, `HubGeneratedSection`): a hand-written page whose `generated-*` slots and child pages a generator fills (an `.md` for such a slot is an error). Home (`''`, see Features and homepage). Issues (`issues/`): a page per `docs/issues/*.md` at `/hub/issues/<file name>/` (not in the nav), listed on the section's page grouped by status with the first paragraph of the first section as the summary. Version (`version/`): `package.json`'s versions and codenames and the build commit and time (the dev plugin keeps its first build's time), then `CHANGELOG.md` with its headings one level down and an anchor per entry (`#2026-10-07-impostor-billboard-lod`); its latest entry is `hub-data.js`'s `latestChange`.
- Documentation (`devTools/hub/api/`, p553): the API reference under `/hub/documentation/`, generated from the engine's and the toolkit's JSDoc. `extract.ts` runs TypeDoc's API with `tsconfig.json`'s `typedocOptions` (so `_dbg__*` and `generatedApp*` are left out, as in `yarn docs`) plus `skipErrorChecking`, and caches the JSON model in `.cache/hub/typedoc.json` under a hash of its inputs (the engine and toolkit `.ts`, `src/*.ts`, `tsconfig.json`, `package.json`, `yarn.lock`, the TypeDoc version, `EXTRACT_VERSION`); `render.ts` turns it into an `engine/` and a `toolkit/` subtree, a page per folder (in the nav) and per module (not in the nav: reached from the landing page's folders and A-Z index, search and links). A module next to a folder of the same name (`core/ECS.ts`) has the folder's URL. Each export is an h3 with its anchor (members `#Owner.member`), its signature highlighted by shiki with its types linked, its comment through markdown-it (`html` off), tables for parameters and properties, and a source link (GitHub at the build commit in `public`, `/__open-in-editor` in `dev`). Undocumented exports are listed as "No description", and the folders show their coverage.
  - Links: `api:` in any page's Markdown or markup (`[loadScene](api:loadScene)`): a bare name is an export, a member needs its owner (`api:ECSWorld.addSystem`), a name two modules export needs a module path suffix (`api:PhysicsAPI.createRigidBody`). Unknown or ambiguous fails the build with the suggestions or candidates (`links.ts`). A JSDoc `{@link X}` lands on the same anchor; one that resolves to nothing documented is text, with a warning at its line (three's own classes without one).
  - Search: a document per module, export and class / interface member, found by name only (`symbol`), its first sentence stored as the snippet, clipped at a word to 120 characters (`SEARCH_SUMMARY_MAX_LENGTH`, p605: the summaries were the largest stored field). The API pages aren't in `hub-data.js`'s `pages`. The whole index is 1,006 kB, under the 1 MB warning: the next cut is the stored `path` (130 kB of 255 page paths repeated per document; a path table needs the search dialog's side too).
  - Dev: TypeDoc runs in a child process (`extractProcess.ts`, about 6 s, never in the dev server's process: it blocks the event loop for seconds). An engine or toolkit save only marks the model stale; the next request for an API page (the landing page and the subtrees, not `documentation/code-blocks/`) starts the conversion and gets the "Rebuilding the API documentation…" page (503), which reloads on the `aek:hub` kind `api`. Other pages never wait, and their `api:` links resolve against the last good model (`buildHub({ api: 'last' })`). A failed conversion keeps that model and shows its errors on the API pages.
  - Rendering the whole API takes about a second, so each slot's output is memoized per model hash, mode and commit; a dev rebuild with an unchanged model adds about 25 ms.
  - Validation (p605): after `convert()`, `extract.ts` runs `app.validate()` with `notExported` only (a public signature naming a type the API doesn't export: a `yarn hub:build` warning at the signature's file and line). `invalidLink` is off, since the renderer's own `{@link}` warning covers it, and so is `notDocumented` (the docs ratchet). TypeDoc's validation messages carry no position: `locateValidationMessages` finds the reflection by the name in the message (TypeDoc 0.28's English texts) and drops warnings on inherited members (three's comments). `typedoc-plugin-zod` (`typedocOptions.plugin`, so `yarn docs` too) expands a `z.infer` / `z.input` alias into its fields, giving it the schema constant's comment when it has none; a union alias gets a table per variant (`getTabledVariants`, labelled by a shared literal key: `type: 'PERSPECTIVE'`). Composed aliases (`SkyBoxDef`: `Omit<z.input<…>> & {…}`) stay references.
  - A TypeDoc upgrade re-checks the Documentation pages: the cache hash includes its version (so the model is rebuilt), `model.ts`'s `Kind` numbers are checked against `ReflectionKind` with `satisfies` (a renumbering fails `tsc`), and the renderer reads the serialized JSON model's shape (`JSONOutput`), so look at a module page, a class, a Zod-derived type (`SkyBoxDef`, `CameraProps`), the `{@link}` warnings and the `notExported` ones (their locations come from the messages' text) before and after. Bump `EXTRACT_VERSION` when what the extraction writes changes.
