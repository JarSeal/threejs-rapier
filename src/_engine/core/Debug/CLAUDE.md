Notes for the debug tooling (`src/_engine/core/Debug/`, its public entry points in `src/_engine/debug/`): the Debug system's detail, moved from the root, where its dual-layer pattern stays; the root `.claude/CLAUDE.md` keeps the project-wide rules, commands and workflow.

## Debug system

- About Ækasha dialog (`core/Debug/_dbg__About.ts`, `openAboutDialog()`): the Æ button left of undo / redo (`_dbg__OnScreenTools.ts`) opens it. It shows `PROJECT_METADATA` (versions, `packages`, `buildTools`, `build`: commit and time, read from git and package.json by `getProjectMetadata` in `devTools/projectMetadata.ts`, which `vite.config.ts` and the Hub share) the runtime (renderer, GPU, browser) and physics (the backends, thread, transport, SharedArrayBuffer, stepping settings, body counts), with a "Copy info" button for bug reports. A new runtime package shows up by itself (`dependencies`), and a new physics backend through its `ENGINES` entry's `name` and `packageName`; a new runtime fact goes in its Runtime or Physics section.
- The other default debug keys (`core/Input/DefaultDebugKeyBindings.ts`, rebindable through `AppConfig.debugKeys`): F1 debug camera, u / i the Debug key shortcuts dialog's App / Aekasha tab, o / p the on-screen camera / scene dropdown (`createDropDown` in `core/UI/DropDown.ts`: an in-page list, not a native select, so Escape cancels; its default styles in `DropDown.scss` are in `:where()`, so any class overrides them), F5 play in prod test mode, F6 main loop, F7 app loop pause, F8 profiler window, F9 env ball, F10 axes gizmo. F1 (and the on-screen camera switch) and F6/F7 and the gizmo keys show a toast (`addDebugToast` in `debug/DebuggerGUI.ts`, a no-op before the debug toaster exists); with the main camera active, a gizmo key on a hidden gizmo also turns on its "in main camera" option. Production test mode has F5 (stop), F6, F7 (no toasts) and F8 (when the profiler is enabled there), which give way to an app binding of the same key (`yieldToOtherBindings`). The Debug tools tab's "Debug key shortcuts" buttons open a dialog (`core/Debug/_dbg__DebugKeyShortcuts.ts`) listing the app's key bindings for the current scene and every engine key by `category`, with what CONFIG.ts or app code changed about it; give a new default key a `category`. It opens with `closeOnEscape` (an `openDialog` opt-in, `core/UI/DialogWindow.ts`): while such a dialog is open, Escape only closes the topmost one and no key binding or other Escape listener gets the press (its keyup included).
- Character debugging (`core/Debug/Character/`): the Character state window (`_dbg__CharacterStateWindow.ts`, opened from a character's edit window or its row toggle in the Characters tab) shows its `data`, and its second header row toggles in-world gizmos (`_dbg__CharacterGizmos.ts`) drawn from `CharacterController.probes`, the controller's last floor ray and wall cast as it used them. A character's gizmo lines belong to its owners, the window and the pin (the window's pin button or the Characters tab's row toggle), and are disposed with the last one. They are refilled by a system at `APP_RENDER_SYNC` / `POSE_CONSUMERS`, so they start from the visual's pose of the frame being drawn. Pins are per character id and session only: restored on character creation, dropped at a scene enter without the character. The window's Properties (`_`) rows are editable: every write goes through `applyConfigValues` (the controller's `config.onChange` recomputes derived values; `config.bakedKeys` are shown locked), is undoable (`character.config`) and is saved per scene and character id in `AEK_debugCharConfig` (`_dbg__CharacterConfigOverrides.ts`, values that differ from `initialConfig` only). A controller applies the saved values with `applySavedCharacterConfig(character)` right after assigning `character.controller`.
- Test bridge (`debug/TestBridge.ts` → `core/Debug/_dbg__TestBridge.ts`, `_DONE_p601` Phase 2): `window.__AEK_TEST__`, installed with `?aekTest=true` in the debug env and prod test mode (never in a production build), from `InitEngine` right before the app's start callback, so it sees the first load. It's what `yarn verify:scenes` drives: `whenSceneReady()` (the first load finished, physics hold released, two frames; reports the `backend`), `whenProbeDone({ freeze? })` (the probe's report through `onPhysicsProbeReport`; `freeze: true` freezes in the report's own frame), `freeze()` (pins physics interpolation to the newest snapshot for two frames, `setPhysicsInterpolationPinnedToNewest`, then pauses the app and master loops and the day-night cycle) and `snapshot({ width, height })` (`takeSnapshotAsync`, a byte-exact PNG, base64). Bump `TEST_BRIDGE_VERSION` when a method's arguments or results change. On install it starts the test clock: every frame advances 1/60 s (`setFixedFrameDelta` in `MainLoop.ts`, which physics stepping follows too, so one step per frame), and it replaces `NodeFrame.prototype.update` so TSL `time` does the same and stops on freeze (three r186's fields: re-check on a three upgrade). So what a page shows depends on how many frames ran, not how long they took.
- Profiler window (`debug/Profiler.ts` public API, implementation `core/Debug/Profiler/`, `_DONE_p344`): a draggable window (`aekProfiler`) opened by `toggleProfilerWindow()` from the on-screen stats panels (setting `openFromStatsPanels`), the Statistics tab, the speedometer button in the top on-screen tools and F8. Its tabs are `DebuggerTabDef`s with the drawer's contract minus `sceneId`: `createProfilerTab` / `openProfilerTab` / `updateProfilerTab` / `isProfilerTabOpen`, ordered by `orderNr` (Overview 0, Objects 10, GPU memory 20, Settings 100). The drawer and the window each mount tabs through a `createTabHost` (`core/Debug/_dbg__TabHost.ts`). Settings are in `AEK_debugProfiler`, the open tab in `AEK_debugProfilerUI`. It loads in the debug env, and in prodTest when its stored `enabledInProdTest` is on (`isProfilerLoadedInThisMode`, read from LS at boot); gate profiler-only registrations on that, not on `IS_DEBUG_ENV`.
  - A closed profiler measures nothing: the frame probe (`setFrameProbe` in `MainLoop.ts`, all three loops) is set only while the window is open, and a tab holds its stats sources only while mounted. Engine and toolkit code adds figures with `registerStatsSource({ id, label, acquire?, release?, read, availability? })`: refcounted, `release` turns off only what `acquire` turned on, and `availability` returns why it is n/a ("WebGPU only"). The built-in ones are in `Profiler/_dbg__ProfilerSources.ts` (GPU frame time through `_dbg__GPUTimer`, draw counters from a `LATE_MAIN` sampler, physics step stats through the runtime `setPhysicsStepStatsEnabled`, memory, rays, PostFX, long tasks, scene).
  - The in-view census (`Profiler/_dbg__Census.ts`) repeats three r186's `_projectObject` culling against the active camera, at the update rate; a three upgrade can make it drift, and `info.render` ("drawn") stays the ground truth. Debug code that adds objects to the root scene marks them with `markDebugHelper(obj)`, so the census counts them in their own row. `registerEntityWindowOpener` lets the Objects tab's heaviest rows open an entity's edit window.
- GPU memory tab (`core/Debug/_dbg__GPUMemory.ts`, `_DONE_p345`): a tab of the profiler window (`createProfilerTab`, id `gpuMemory`; open it with `openProfilerTab(GPU_MEMORY_TAB_ID)`), not the drawer. It loads where the profiler does (`isProfilerLoadedInThisMode`: the debug env, and prodTest when the profiler is enabled there; prodTest has no budget toast and no links to drawer tabs). Its sampler and peaks run with the window closed too. three's own `renderer.info` bookkeeping, not a driver figure. Frame counters are read by a debug `LATE_MAIN` system right after the render (three resets `info.render` in its own animation frame). "By owner" sums registered assets (`AssetOwners`) and sources with three's per-object bytes (`info.memoryMap`), so they and "untracked" add up to `info.memory.total`. A GPU resource that isn't a registered asset (a render target, an instance buffer) should be named with `registerGPUMemorySource({ id, label, getResources, owner? })` (`debug/GPUMemory.ts`, a no-op where the profiler doesn't load, returns its remover): `getResources` returns the three objects (textures, render targets, geometries, attributes), never a byte estimate. The snapshot diff names what a scene visit left allocated, through an allocation tracker that wraps `renderer.info`'s create / destroy calls (installed by `onRendererCreated` in `core/Renderer.ts`, before `renderer.init()`). three r186 counts compressed textures as 1 B and cube faces as 1×1. The tab fixes the first at the source: `installCompressedTextureSizer` (`_dbg__GPUMemoryOwners.ts`, also before `init()`) replaces `info._getTextureMemorySize` so a compressed texture counts its uploaded mip bytes, in every figure. The cube part is estimated separately, outside the totals.
- Drawer tabs are one declarative `createDebuggerTab({ id, title, icon, content, ... })` call (`debug/DebuggerGUI.ts`; implementation `core/Debug/_dbg__DebuggerGUI.ts`). `content` is a factory (re-run on every mount/rebuild) returning sections: CMPs, `{ pane: true, content: [...] }` declarative Tweakpane panes (`_dbg__DebuggerPaneBuilder.ts`: bindings, folders, buttons, separators, a `custom` escape hatch) and `debuggerListCMP` lists (`_dbg__DebuggerList.ts`, with optional per-row icon toggles). Menu order is `AppConfig.debugDrawer.tabOrder` (engine default `DEFAULT_DEBUG_DRAWER_TAB_ORDER` in `core/Config.ts`), overridable per tab with `orderNr` (same 0-based scale).
  - `openDebuggerTab(id)` opens the drawer on a tab. Refresh with `updateDebuggerTab(id, { rebuild? })`: it's a no-op unless that tab is visible (`isDebuggerTabOpen(id)`); a closed tab is rebuilt from `content` on its next mount. Use `refreshIntervalMs` (runs only while visible) and `onOpen` (returns its cleanup) instead of hand-rolled intervals/teardown, and `onRefresh` to sync live values into the objects panes bind to.
  - Scene-scoped tabs: `sceneId` removes the tab on that scene's exit (one drawer rebuild); the saved open tab id is kept, so the drawer lands on the tab again when the scene re-creates it, also after a reload. Create them from the scene file, debug env only, via a dynamic `import()` of an `_dbg__` module (eg. `app/_dbg__spaceDemo.ts`).
  - Persistence: `lsKey` + `state` + `persistKeys` — only those state keys are hydrated (synchronously at registration, also in prod test mode) and written (on a finished change) as a flat object; bindings can use one-level paths (`'helpers.showGrid'`). Folder open states go to `uiLsKey` (default `${lsKey}UI`). Binding `onChange` fires on user input only (never on hydration/refresh/rebuild) and gets `e.prev`/`e.last` for undo recording. Scene-scoped, boot-time and deviation-only keys stay module-owned (custom `headerButtons` for their clear-LS buttons).

This debug drawer (`src/_engine/debug/`, `src/_engine/core/Debug/`) is under active rewrite on the current branch (`legacy-refactoring-camera-mesh-light-debug-tools`) to align it with the ECS architecture — expect WIP rough edges here. Legacy (pre-ECS) Camera/Light/Mesh managers have already been fully removed in favor of ECS-based `CameraManager.ts`/`LightManager.ts`/`MeshManager.ts` in `src/_engine/core/`; favor ECS patterns for any new manager-like code rather than reintroducing non-ECS managers.
